# REVIEW-1.2 — an outside critic reads Quill 1.2

**Reviewed 2026-10-23, read-only.** Written by the critic agent the owner asked for (a codex
worker in the `leaffish` worktree), with the brief *be a critic and be very creative*; kept here
as it was written, so the findings can be checked against the code rather than remembered.

**Reviewed:** `Rasmus-03/1.2` at `d7ab447` (`1.2/docs: the progress docs tell the Danish truth`). I read the release plan and claims against source, tests, workflows and docs; I did not build or run the app.

## The one thing

The release's trust story contradicts itself in the places a newcomer actually reads: the changelog says Danish is complete and all 71 real documents round-trip, but the README still says Danish is absent and attributes the corpus to four producers, while every manifest URL is from Apache POI. More seriously, the maths controls and many errors remain English by design, and the passing translation test explicitly skips the Math tab. A Danish student choosing Quill from its front page will encounter a product that calls itself Danish, a help page that says it is not, and a calculator whose failure vocabulary switches back to English.

## Findings

**Index:** F1 contradictory release claims; F2 maths is still English at the point of failure; F3 corpus gate can pass without a corpus; F4 corpus checks content more narrowly than “survives everything”; F5 Danish terminology needs a human pass; F6 release path is not exercised or reproducible from the docs; F7 first-use ribbon buries common actions; F8 remaining trust gates do not prove shipped behavior.

### F1 — The front page tells Danish users the opposite of the release

The README's “Not yet” row says Danish is not among the 19 interface languages, while it is registered in `i18n/mod.rs` and the new Danish catalog. The same README says the corpus contains files “from Word, Google Docs, LibreOffice and Pages”; the manifest has 71 URLs, all under `apache/poi`. Its catalog number is 489/504 while the current generated parity claim is 497/504. The status page says the corpus is checked “on every build” and is ready for daily use, but the test silently passes without corpus files (F3). A student, teacher or evaluator cannot tell what the release actually contains. **Where:** `README.md:80-83`; `docs/status.md:16-18`; `crates/ui-egui/src/i18n/mod.rs:55`; `crates/docx/tests/corpus-manifest.tsv` (all rows); `docs/release-plan-1.2.md:415-423`. **Size: S. Cheapest honest fix:** synchronize README/status/parity figures and state precisely that this is a POI corpus, optional in ordinary CI, with no page comparison yet.

### F2 — The maths tab's errors switch back to English

The core controls have Danish labels, but validation and operation failures are still user-facing English: for example, `Select e.g. …`, `Taylor order must be at most 1000`, `Could not solve ODE`, and `Defined {name}`. The translation test excludes every command located under `Math`, so its green result cannot support the claim that maths labels/messages are Danish. A student who makes a normal input mistake gets the English interface exactly when they need help. **Where:** `crates/engine/src/cmd/mathcraft.rs:2815, 2851, 2855, 2886, 2944`; `crates/ui-egui/src/i18n/tests.rs:141-150`; the release claim is `CHANGELOG.md:32-38`. **Size: M. Cheapest honest fix:** centralize user-facing math messages behind the existing UI localization layer (or Danish-aware message mapping), translate the high-frequency validation and failure paths first, and add tests that enumerate them rather than excluding the namespace. If any remain English, say so in the release notes.

### F3 — The corpus test succeeds when it checks nothing

`corpus.rs` returns normally when its directory is absent, printing that the round trip was not checked. The regular CI workflow runs workspace tests but never fetches the corpus or sets `QUILL_DOCX_CORPUS`; thus its green status says nothing about the corpus. This directly conflicts with “checked on every build” in `docs/status.md` and the definition-of-done language. **Where:** `crates/docx/tests/corpus.rs:213-224`; `.github/workflows/ci.yml:43-47`; `docs/docx-corpus.md:21-22`. Reproduce with `cargo test -p wordcraft-docx --test corpus` in a checkout without `corpus/docx`: it passes with “not checked.” **Size: S. Cheapest honest fix:** give corpus validation its own scheduled or dedicated CI job that fetches the hash-pinned files and fails if the directory is empty; keep the local optional behavior if needed.

### F4 — “Round-trip survives” measures a small projection of a document

The corpus predicate compares paragraph text, table row/cell counts and text, flattened text in parts, and the multiset of media bytes. It does not compare page count/rendering, formatting, fields and their codes/results, section/page settings, hyperlinks/relationships, drawing positions, content-control metadata or revision state. Its third/fourth read stability check compares only body text and table shape. A contract with intact words but lost numbering, pagination or clause emphasis can pass. The plan's B1 acceptance criteria asked for render, paragraph/table structure and page count; that is not what this harness implements. **Where:** `crates/docx/tests/corpus.rs:77-112, 183-208`; plan `docs/release-plan-1.2.md:155-164`; the user-facing scope is described in `docs/docx-corpus.md:63-68`. **Size: M/L. Cheapest honest fix:** narrow the claim to the four measured content classes now, and add independent checks for formatting/fields/sections plus a rendered page-count or screenshot comparison before saying documents survive in the user's sense.

### F5 — The Danish is plausible in bulk, but several visible terms sound translated

This is not a claim that all 2,495 strings are bad: many everyday choices are clear and natural (`Gem`, `Indsæt`, `Punktopstilling`, `Sideskift`). But no native-speaker review is recorded, and these ten visible choices deserve review before a Danish school release. Suggested neutral Danish wording is illustrative, not a claim about proprietary UI strings: **“Vault” → “Boks”** (physical box; describe it as an Obsidian-mappe or vault), **“Cloud” → “Cloud”** (English in a core pane; use “Skylagring”), **“Match Fields” → “Match felter”** (verb-like English calque; “Sammenkæd felter” conveys the action), **“Differential” → “Differential”** (untranslated mathematical noun; use a Danish term/description), **“Differential theta/x/y”** (same English residue), **“Ceiling” → “Loft”** (literal roof, not a math operation; say “afrunding opad” or a symbol-specific description), **“Editor” → “Editor”** (English where a Danish role label exists), **“Highlighter” → “Overstregningstusch”** (reads as crossing out; describe text marking/highlighting), **“Backlinks” → “Tilbagelinks”** (opaque calque; say “Indgående links”), and **“Vault Tags” → “Bokstags”** (unnatural compound built on the same misleading “boks”). “Matrix” may be acceptable technical Danish, so it is not in the ten. **Where:** `crates/ui-egui/src/i18n/da.tsv:241,324,432-433,1276,1298-1301,2458-2471,2499,2504-2505`; release plan explicitly leaves native review open at `docs/release-plan-1.2.md:451-452`. I did not consult Word's Danish UI, and the clean-room rule forbids copying its localized wording; a Danish teacher can check these suggestions against ordinary Danish and the requested terminology list without copying product text. **Size: S/M. Cheapest honest fix:** a one-hour native-speaker pass over the maths, navigation and ribbon terms, then terminology tests for the selected glossary.

### F6 — A stranger cannot follow the release recipe to a proven release

The release plan says there is no `release` branch and the workflow has never run; `release.yml` only triggers on pushes to that branch (or manual dispatch). The documented dry run on another branch intentionally produces no draft release, and signing jobs are blocked by the environment's branch rule. The docs point to an external playbook and a secrets setup on the release manager's machine, so cloning the tree alone cannot reproduce a release, verify signing, or complete the promised publish checklist. The checklist itself remains unchecked. **Where:** `docs/release-plan-1.2.md:447-450`; `.github/workflows/release.yml:12-16,22-24`; `docs/releasing.md:22-31,63-84`; `docs/release-plan-1.2.md:424`. **Size: M. Cheapest honest fix:** record a successful unsigned dry run with artifacts and job links, document which steps require owner-only credentials, and do not describe the release workflow as proven until one run on the release branch succeeds.

### F7 — The first-use Home ribbon gives its largest space to low-frequency tools

Home begins with Clipboard, Font and Paragraph, then Styles and Editing, but its last two large groups are Voice/Dictate and Editor/Spelling. Meanwhile a first-time school user has no obvious Home button for Insert Table or Insert Picture, common actions in a worksheet/report, and no visible Word Count despite the product emphasizing writing. Those actions exist on Insert or the status bar, but the first five minutes require hunting across tabs. This is a product discovery issue the command catalog cannot measure. **Where:** `crates/ui-egui/src/ribbon.rs:506-768` (Home layout); `crates/ui-egui/src/ribbon.rs:770+` (Insert groups); the included sample/template pathways are in `crates/engine/src/sample.rs`. **Size: S/M. Cheapest honest fix:** move or add compact Insert Table/Picture and Word Count affordances to Home, and demote Voice/Editor if they are not core audience workflows; inspect a Danish screenshot before finalizing.

### F8 — Green gates still leave the decisive release questions open

CI runs fmt, clippy, workspace tests, Maxima tests, assets, layers and wasm, but none proves native-reader behavior on macOS/Windows, a real user's Danish proofreading dictionary is installed, a screen reader understands the canvas, page breaks match Word, or a package can be installed/launched on each target. The plan explicitly says the Windows MSI needs Windows, the first fuzz run is still owed, no native-speaker review occurred, the page-by-page DOCX comparison remains open, and the final release checklist has not been walked. These are not reasons to distrust every feature; they are concrete limits to what “trustworthy again” and green CI can mean. **Where:** `docs/release-plan-1.2.md:398-424, 447-452`; `.github/workflows/ci.yml:25-60`; `docs/localization-parity.md:32-35, 45-48`; `docs/ui-parity.md:43`. **Size: M. Cheapest honest fix:** retain an explicit release evidence sheet with platform smoke checks, a Danish dictionary-present/absent check, one screen-reader pass, and the first fuzz run; keep unsupported claims marked partial until each is evidenced.

## The Danish verdict

The interface is mostly Danish in the ordinary ribbon and dialogs: `Gem`, `Indsæt`, `Punktopstilling`, `Fremhævningsfarve` and `Sideskift` are immediately legible. It is still English in a Danish coat in the maths feature's errors, despite the Danish button names, and the translation test has an explicit Math exemption. Recent Obsidian terms (`Boks`, `Boks-tilbagelinks`, `Bokstags`) make a software concept sound like a literal container, while `Cloud`, `Editor` and some mathematical vocabulary remain English. Danish proofing itself is a useful genuine addition, but spelling is only active if a compatible Hunspell dictionary is installed; without one the code deliberately accepts every word. My verdict: a real Danish interface foundation, not yet a professionally reviewed Danish school product. A native review is release work, not a post-release nicety, because the plan itself says machine translation is unacceptable.

## What I could not check

I did not build or launch the app, fetch the corpus, render documents, install a Danish dictionary, or run a screen reader. I did not run `cargo xtask ci` or a release build, as requested. I did not access Word's UI; Danish alternatives above are independent editorial suggestions, not transcriptions of Word. I could verify the manifest sources from the committed URLs and read the comparison logic, but not independently inspect the external DOCX contents.

## What is genuinely good

The repository now has a broad Danish catalog and real Danish proofing code, and the math solver's four important empty-solution outcomes have dedicated Danish messages and tests. The corpus is pinned by hashes, kept outside the repository, and uses real third-party documents rather than self-authored XML fixtures. CI has materially better breadth than a library-only test job, including hostile-input tests and browser compilation; the plan is candid about unproven platform and fuzz evidence even when adjacent summary prose overclaims.

## Surprises

The sharpest surprise is that the test designed to prove every command is translated explicitly removes the Math feature before checking it; a green “translation coverage” badge can therefore coexist with the most important feature for the Danish-school pitch showing English errors. The second is that the corpus “every build” guarantee can be a no-op success, while its result is then presented as evidence that documents from four different producers are covered. The third is the human-facing trail: README, status, release plan and changelog describe different products, and the release checklist admits the branch and final rehearsal do not exist yet.
